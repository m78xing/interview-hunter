# 面试猎手 (Interview Hunter) - 项目细节

## 1. 项目概述

### 1.1 项目定位
面试猎手是一个**智能面经学习系统**，旨在帮助用户高效采集、复习和管理面试知识。

### 1.2 核心特性
- **智能采集**: 自动爬取牛客网、小红书面经
- **卡片生成**: LLM 提取 Q&A 卡片
- **遗忘曲线**: SM-2 算法调度复习
- **多因子推荐**: 遗忘曲线 + 薄弱点 + 岗位热度 + 知识依赖
- **LLM 审计**: 自适应调整学习策略
- **对话学习**: 基于向量搜索的智能问答学习界面

### 1.3 技术栈
- **前端**: Streamlit
- **后端**: Python asyncio
- **LLM**: DeepSeek Chat
- **向量数据库**: Chroma
- **关系数据库**: SQLite
- **嵌入模型**: 支持 OpenAI/Cohere/Mock

## 3. 核心模块详解

### 3.1 CollectionOrchestrator (采集编排器)

**职责**: 协调整个系统的数据采集、分析、存储和调度。

**核心组件**:
- `HeartbeatDriver`: 定时触发采集任务
- `CheckpointManager`: 状态持久化

**心跳机制**:
```python
# 每天 08:00 触发 (可配置)
scheduled_times = ["08:00"]
cooldown_on_error = 30  # 错误后冷却 30 分钟
```

**主流程**:
```
_on_heartbeat()
  ├── _run_collection_cycle()  # 采集→分析→存储
  │   ├── preference_store.get_keywords()
  │   ├── collector.collect()
  │   ├── analyzer.analyze()
  │   ├── 去重检查 (Chroma)
  │   └── 存储 (SQLite + Chroma)
  └── _run_daily_audit()       # 每日审计
      └── scheduler.trigger_daily_audit()
```

### 3.2 CollectorWorkflow (采集工作流)

**职责**: 从牛客网、小红书等平台爬取面经。

**数据来源**:
| 平台 | 爬虫 | 特点 |
|------|------|------|
| 牛客网 | nowcoderSpider | AJAX API + DOM 解析 |
| 小红书 | XHSSpider | Playwright (需登录) |
| 备用 | _collect_mock() | 模拟数据兜底 |

**关键方法**:
```python
async def collect() -> List[RawPost]:
    for keyword in keywords:
        posts = await _collect_keyword(keyword)
        all_posts.extend(posts)
    return all_posts
```

**关键字匹配**:
```python
def _title_matches_keyword(title, keyword):
    # "大模型 面经" → ["大模型"]
    parts = keyword.lower().replace(' 面经', '').split()
    return any(p in title.lower() for p in parts)
```

### 3.3 AnalyzerWorkflow (分析工作流)

**职责**: 从面经中提取 Q&A 卡片。

**处理流程**:
```
RawPost → LLM 提取 → 规则 fallback → 去重检查 → Card
```

**LLM 提取**:
- API: DeepSeek Chat
- Prompt: 提取 3-5 个核心问题 + 详细答案
- 输出: JSON 格式 (cards: question/answer/difficulty/tags)

**去重机制**:
| 阈值 | 用途 |
|------|------|
| 0.92 | 精确重复 → 跳过 |
| 0.75 | 相似 → 保留但标记 |

**规则 fallback**:
```python
# 无 LLM 时使用正则提取
patterns = [
    r'[\d一二三四五六七八九十]+\.\s*(.+)',  # 1. 2. 3.
    r'问[：:]\s*(.+)',                       # 问:
    r'(.+?)\?\s*',                          # 问题?
]
```

### 3.4 SchedulerWorkflow (调度工作流)

**职责**: 管理学习会话和复习调度。

**核心功能**:

1. **会话管理**
```python

  → 获取所有卡片
  → 按 created_at 倒序
  → 可按公司过滤
  → 返回卡片队列
```

2. **复习记录**
```python
record_review(card_id, quality, time_taken)
  → add_review_log()
  → update_ease_factor()  # SM-2 算法
  → _check_threshold_trigger()  # 触发审计
```

3. **SM-2 间隔算法**
```python
# 质量评分: 0-5 (低于 3 为错误)
EF_new = EF_old + (0.1 - (5 - quality) * (0.08 + (5 - quality) * 0.02))
EF = max(1.3, EF_new)  # 最小值

if quality < 3:
    interval = 1  # 错误则 1 天后复习

4. **每日审计**
```python

  → 收集统计 (today_reviews, week_correct_rate, tag_error_rates)
  → 调用 LLMAuditor.audit()

5. **多路径检索**
```python

  → RagManager.search()  # 5 条路径
  │   ├── semantic (向量)
  │   ├── keyword (TF-IDF)
  │   ├── recent (时间)

  │   └── similar_tags (标签)

```

## 6. 关键算法

### 6.1 SM-2 间隔算法

**来源**: SuperMemo 2 遗忘曲线算法 ( Piotr Wozniak, 1987)

**公式**:
```python
# EF 更新
EF = EF + (0.1 - (5 - quality) * (0.08 + (5 - quality) * 0.02))
EF = max(1.3, EF)

# 间隔更新
if quality < 3:  # 错误
    interval = 1
else:            # 正确
    interval = max(1, old_interval * EF)
```

#### 参数详解

| 参数 | 值 | 设置原因 |
|------|-----|----------|
| **EF 初始值** | 2.5 | SM-2 标准默认值，表示"中等难度" |
| **EF 最小值** | 1.3 | 防止难度因子过低导致间隔为 0 |
| **EF 增量公式** | `0.1 - (5-q)*(0.08 + (5-q)*0.02)` | 非线性调整：质量越差惩罚越重 |
| **quality 阈值** | 3 | 低于 3 视为错误，需要重置间隔 |
| **最小间隔** | 1 天 | 确保至少有 1 天复习间隔 |

#### 公式推导

```
设 q = quality (0-5)

EF 变化量 = 0.1 - (5-q) * (0.08 + (5-q) * 0.02)

质量 q=5 (完美):
  EF 变化 = 0.1 - 0 = +0.10 (间隔快速增加)

质量 q=4 (正确):
  EF 变化 = 0.1 - 1*(0.08+0.02) = 0.10 - 0.10 = 0 (保持)

质量 q=3 (困难):
  EF 变化 = 0.1 - 2*(0.08+0.04) = 0.10 - 0.24 = -0.14 (轻微惩罚)

质量 q=1 (错误):
  EF 变化 = 0.1 - 4*(0.08+0.16) = 0.10 - 0.96 = -0.86 (大幅降低)
```

#### 设计合理性

1. **惩罚不对称**: 错误惩罚远大于正确奖励 → 促使学习者更认真地对待复习
2. **指数间隔**: `interval * EF` 产生指数增长 → 符合遗忘曲线特性
3. **下限保护**: EF >= 1.3 防止卡片"死亡"（永远不再出现）

### 6.2 Reciprocal Rank Fusion (RRF)

**公式**:
```
RRF_score(doc) = Σ weight_i * (1 / (k + rank_i(doc)))
```

#### 参数详解

| 参数 | 值 | 设置原因 |
|------|-----|----------|
| **k** | 60 | RRF 标准值，降低排名靠前文档的优势 |
| **语义权重** | 0.40 | 语义匹配最重要，占比最高 |
| **关键词权重** | 0.25 | 精确匹配次要 |
| **最近权重** | 0.15 | 时间因素辅助 |
| **公司权重** | 0.12 | 目标公司相关 |
| **标签权重** | 0.08 | 标签匹配权重最低 |

#### k=60 的作用

```
假设文档 A 在路径1排第1，在路径2排第3

k=10 时: 1/(10+1) + 1/(10+3) = 0.0909 + 0.0769 = 0.168
k=60 时: 1/(60+1) + 1/(60+3) = 0.0164 + 0.0159 = 0.032

k 越大，各路径贡献越均衡，避免单一路径主导结果
```

#### 路径权重设计逻辑

```
权重分配依据:
1. 语义 (0.40): 向量相似度最准确反映用户意图
2. 关键词 (0.25): 精确匹配补充语义召回
3. 最近 (0.15): 新内容可能更有价值
4. 公司 (0.12): 目标导向，辅助筛选
5. 标签 (0.08): 粗粒度分类，补充覆盖
```

#### 多样性保证

RRF 相比简单平均的优势：
- 某路径失效时，其他路径仍能贡献
- 排名靠前文档不会完全主导结果
- k=60 平滑多路径贡献曲线

### 6.3 多因子推荐

**评分因子**:
```python
score = (
    w1 * retrievability +   # 遗忘曲线 (SM-2)
    w2 * weakness +         # 薄弱点
    w3 * hotness +           # 热门度
    w4 * dependency          # 知识依赖
) - diversity_penalty       # 多样性惩罚
```

## 11. 核心模块实现方法

### 11.1 HeartbeatDriver (心跳驱动)

**技术栈**: APScheduler (后台调度器)

**架构说明**:
- 使用 `APScheduler` 的 `BackgroundScheduler` 作为底层调度器
- 采用 `CronTrigger` 触发器，按 cron 表达式（小时:分钟）调度任务
- 调度器运行在**后台线程**中，不阻塞主线程
- 支持多时间点配置（如每天 08:00 和 20:00）

**工作流程**:

```
┌─────────────────────────────────────────────────────────────┐
│ HeartbeatDriver 生命周期                                    │
├─────────────────────────────────────────────────────────────┤
│ 1. 初始化 ( __init__ )                                      │
│    - 创建 BackgroundScheduler (daemon=True)                 │
│    - 设置 scheduled_times (默认 ["08:00"])                   │
│    - 设置 cooldown (默认 60 分钟)                            │
│                                                             │
│ 2. 启动 ( start() )                                         │
│    - 校验 on_tick 回调已设置                                 │
│    - 为每个 scheduled_time 创建 CronTrigger job            │
│    - 添加到 APScheduler 调度队列                            │
│    - 启动调度器线程                                          │
│    - 计算下次执行时间 next_run                               │
│                                                             │
│ 3. 执行 ( _execute_task )                                   │
│    - 状态切换: IDLE → RUNNING                               │
│    - 调用 on_tick 回调 (同步调用)                            │
│    - 成功: 重置连续错误计数                                   │
│    - 失败: 连续错误计数 +1                                   │
│    - 状态切换: RUNNING → IDLE                               │
│    - 重新计算下次执行时间                                     │
│                                                             │
│ 4. 触发 ( trigger_now )                                     │
│    - 立即执行 _execute_task                                  │
│    - 跳过调度等待                                            │
└─────────────────────────────────────────────────────────────┘
```

**关键特性**:

| 特性 | 说明 |
|------|------|
| 调度方式 | 后台线程 (BackgroundScheduler) |
| 触发方式 | CronTrigger (固定时间) |
| 并发控制 | max_instances=1，防止重复执行 |
| 错误处理 | 连续错误计数 + 冷却期 |
| 状态查询 | get_status() 返回运行状态 |

**执行时序图**:
```
用户/系统                   HeartbeatDriver              APScheduler
  │                            │                             │
  │  set_on_tick(callback)    │                             │
  │──────────────────────────>│                             │
  │                            │                             │
  │  start()                  │                             │
  │──────────────────────────>│  add_job(cron)               │
  │                            │────────────────────────────>│
  │                            │                             │
  │                     [等待定时触发]                       │
  │                            │                             │
  │                     [08:00 到达]                        │
  │                            │  _execute_task()            │
  │                            │<────────────────────────────│
  │                            │                             │
  │                            │  on_tick() (同步调用)       │
  │                            │───────────────────────────>│
  │                            │                             │
```

### 11.2 RecommendationEngine (推荐引擎)

**技术栈**: 自研多因子评分算法 + SQLite 数据查询

**架构说明**:
- 离线计算模式：每次推荐时实时计算分数
- 四大评分因子加权求和
- 多样性惩罚防止同标签卡片连续出现
- 标签层级依赖关系防止基础不牢

**评分因子说明**:

| 因子 | 计算方式 | 数据来源 |
|------|----------|----------|
| **Retrievability** | 基于上次复习时间与间隔的比值 | SQLite card_stats |
| **Weakness** | 错误次数/总复习次数 | SQLite card_stats |
| **Hotness** | 目标公司匹配 + 热门标签 | SQLite cards + 实时统计 |
| **Dependency** | 父标签掌握度 < 0.5 则降低 | SQLite tag_stats |

**工作流程**:

```
┌─────────────────────────────────────────────────────────────┐
│ RecommendationEngine.recommend() 流程                       │
├─────────────────────────────────────────────────────────────┤
│ 1. 获取候选卡片                                              │
│    sqlite.get_due_cards(limit * 2)                           │
│    → 获取待复习卡片 ID 列表                                  │
│                                                             │
│ 2. 遍历候选卡片                                              │
│    for card_id in candidates:                               │
│      - 获取卡片内容                                         │
│      - 计算四个因子分数                                      │
│      - 计算多样性惩罚                                        │
│      - 加权求和得到总分                                      │
│                                                             │
│ 3. 排序                                                      │
│    按 (总分 desc, 创建时间 asc, ID asc) 排序                 │
│                                                             │
│ 4. 多样性筛选                                                │
│    - 维护最近展示的标签队列 (recently_shown_tags)            │
│    - 跳过全部标签都在最近队列中的卡片                         │
│    - 确保推荐的标签多样性                                    │
│                                                             │
│ 5. 返回结果                                                  │
│    返回 Top-K 卡片及详细评分                                │
└─────────────────────────────────────────────────────────────┘
```

**算法公式**:
```
score = w1*retrievability + w2*weakness + w3*hotness + w4*dependency - diversity_penalty

默认权重:
- retrievability: 0.35
- weakness: 0.30
- hotness: 0.20
- dependency: 0.15

diversity_penalty: 0.5 (如果卡片所有标签都在最近展示过)
```

### 11.3 RagManager (RAG 管理器)

**技术栈**: Chroma 向量库 + SQLite + RRF 融合算法

**架构说明**:
- 五条独立检索路径并行执行
- 使用 RRF (Reciprocal Rank Fusion) 算法融合结果
- 支持可选路径（company, tags）
- 向量嵌入缓存减少重复计算

**检索路径说明**:

| 路径 | 技术实现 | 用途 |
|------|----------|------|
| **Semantic** | Chroma 向量相似度检索 | 语义匹配 |
| **Keyword** | 简单词匹配 + TF-IDF | 精确关键词 |
| **Recent** | SQLite 按时间排序 | 最新内容 |
| **Company** | Chroma metadata 过滤 | 按公司筛选 |
| **Tags** | 标签集合交集计算 | 相关主题 |

**工作流程**:

```
┌─────────────────────────────────────────────────────────────┐
│ RagManager.search() 流程                                     │
├─────────────────────────────────────────────────────────────┤
│ 1. 并行执行各路径检索                                        │
│    - semantic: query_embedding → chroma.similarity          │
│    - keyword: 词匹配 → 打分                                  │
│    - recent: sqlite.get_recent_cards()                      │
│    - company: (可选) chroma.get_cards_by_tag()              │
│    - tags: (可选) 标签交集计算                               │
│                                                             │
│ 2. RRF 融合                                                  │
│    对每条路径的结果，按排名计算:                             │
│    rrf_score += weight * (1 / (k + rank))                   │
│    k = 60 (RRF 常数)                                        │
│                                                             │
│ 3. 排序取 Top-K                                             │
│    按 rrf_score 降序排列                                     │
│                                                             │
│ 4. 构建结果                                                  │
│    - 包含每条路径的贡献分数                                  │
│    - 可选: explain_result() 生成解释                        │
└─────────────────────────────────────────────────────────────┘
```

**RRF 融合示例**:

```
假设:
- semantic 路径返回: [A, B, C] (排名 1,2,3)
- keyword 路径返回: [B, A, D] (排名 1,2,3)
- recent 路径返回: [C, A, B] (排名 1,2,3)

权重: semantic=0.4, keyword=0.25, recent=0.15

计算 A 的 RRF 分数:
- semantic: 0.4 * (1/(60+1)) = 0.00656
- keyword: 0.25 * (1/(60+2)) = 0.00403
- recent: 0.15 * (1/(60+3)) = 0.00236
- total = 0.01295

同理计算 B、C、D，选择 Top-K
```

### 11.4 MemoryEngine (记忆引擎)

**技术栈**: JSON 文件持久化 + 内存缓存

**架构说明**:
- 磁盘 JSON 文件存储（entries/ + profiles/ 目录）
- 内存字典作为缓存加速查询
- 支持会话维度的记忆管理
- 指数衰减函数模拟遗忘

**记忆维度**:

| 维度 | 描述 | 权重 |
|------|------|------|
| RECENCY | 最近复习时间 | 0.25 |
| FREQUENCY | 复习频率 | 0.20 |
| DIFFICULTY | 难度评估 | 0.20 |
| FATIGUE | 学习疲劳度 | 0.15 |
| MOOD | 学习心情 | 0.10 |
| TIME_OF_DAY | 学习时间段 | 0.05 |
| TOPIC_IMPORTANCE | 主题重要性 | 0.03 |
| WEAK_TAGS | 薄弱标签 | 0.02 |

**工作流程**:

```
┌─────────────────────────────────────────────────────────────┐
│ MemoryEngine 生命周期                                        │
├─────────────────────────────────────────────────────────────┤
│ 1. 初始化 ( __init__ )                                      │
│    - 创建 storage_dir 目录                                   │
│    - 扫描 entries/ 目录加载历史记忆                         │
│    - 扫描 profiles/ 目录加载配置                            │
│                                                             │
│ 2. 更新记忆 ( update_memory )                               │
│    - 创建 MemoryEntry                                       │
│    - append 到内存缓存                                      │
│    - 同步写入 JSON 文件                                      │
│                                                             │
│ 3. 查询记忆 ( get_memory )                                  │
│    - 内存缓存查找 (会话级别)                                │
│    - 可选: 按卡片过滤                                       │
│    - 可选: 按维度过滤                                       │
│                                                             │
│ 4. 衰减计算 ( _apply_decay )                               │
│    - 计算天数差                                              │
│    - 应用指数衰减: decay_rate ^ (days / interval)          │
│                                                             │
│ 5. 记忆摘要 ( summarize_memory )                           │
│    - 统计各维度记忆数量                                      │
│    - 返回配置和统计信息                                      │
│                                                             │
│ 6. 记忆合并 ( consolidate_memory )                         │
│    - 保留最近 N 条                                           │
│    - 删除旧条目节省空间                                      │
└─────────────────────────────────────────────────────────────┘
```

**持久化结构**:
```
memory/engine/
├── entries/
│   ├── session1_card1_recency_1234567890.json
│   ├── session1_card1_frequency_1234567891.json
│   └── ...
└── profiles/
    ├── session1.json
    ├── session2.json
    └── ...

### 11.5 LLMAuditor (LLM 审计)

**技术栈**: DeepSeek API (HTTP 调用) + 定时触发

**架构说明**:
- 两种审计模式：阈值审计 + 每日审计
- 阈值审计：实时检测，复习后立即判断
- 每日审计：定时触发，综合分析
- LLM 生成结构化 JSON 建议

**审计类型说明**:

| 类型 | 触发条件 | 时机 | 用途 |
|------|----------|------|------|
| **阈值审计** | 连续错误 >= 5 且 错误率 >= 0.6 | 每次复习后 | 立即调整 |
| **每日审计** | 新一天且 0-6 点 | 心跳触发 | 策略优化 |

**工作流程**:

```
┌─────────────────────────────────────────────────────────────┐
│ LLMAuditor 生命周期                                          │
├─────────────────────────────────────────────────────────────┤
│ 1. 阈值审计 ( should_trigger_threshold_audit )             │
│    - 检查 consecutive_errors >= threshold                  │
│    - 检查 error_rate >= threshold                          │
│    - 两者同时满足返回 True                                   │
│                                                             │
│ 2. 阈值分析 ( analyze_threshold_audit )                   │
│    - 生成轻量级建议 (无需 LLM)                               │
│    - 建议: 降低难度/推荐基础题                               │
│    - 判断是否需要 LLM 深度审计                               │
│                                                             │
│ 3. 每日审计 ( should_trigger_daily_audit )                 │
│    - 检查上次审计时间                                        │
│    - 新一天且在凌晨 0-6 点返回 True                         │
│                                                             │
│ 4. LLM 审计 ( audit )                                       │
│    - 收集数据: review_stats, tag_error_rates, mastery      │
│    - 构建 Prompt (含数据格式化)                              │
│    - 调用 DeepSeek API                                      │
│    - 解析 JSON 响应                                          │
│    - 保存审计历史                                            │
│                                                             │
│ 5. LLM 调用 ( _call_llm )                                   │
│    - HTTP POST 到 api.deepseek.com                         │
│    - Bearer Token 认证                                      │
│    - timeout: 60s                                           │
│    - 解析 JSON (处理 ```json 前缀)                          │
└─────────────────────────────────────────────────────────────┘
```

**Prompt 模板**:

```

### 最近复习统计
{review_stats}

{current_keywords}

### 薄弱标签
{weak_tags}

### 掌握度矩阵
{mastery_matrix}

## 请给出以下建议（JSON格式）:
{
    "learning_strategy": "学习策略建议",
    "keyword_adjustments": [{"action": "add/remove", "keyword": "关键词", "reason": "原因"}],
    "focus_areas": ["重点领域"],

```
